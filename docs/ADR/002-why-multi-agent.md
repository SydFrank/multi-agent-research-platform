# ADR 002 · 为什么用多 Agent,以及每个 Agent 如何自证价值

- **状态**:已采纳

---

## 背景

多 Agent 架构在实践中经常被滥用:把本可由单 Agent 完成的任务拆给多个 Agent,结果更慢、更贵、更难调试,且无法说明收益来自哪里。

本项目主题即多智能体,因此**必须先证明它在本场景中是必要的**,否则整个架构立不住。

## 问题

1. 本场景是否真的需要多 Agent?
2. 如何防止 Agent 数量无理由膨胀?

---

## 决策一:多 Agent 的必要性,基于四条判据

一个任务值得用多 Agent,需满足以下条件(本项目逐条核对):

| 判据 | 本场景 | 说明 |
|---|---|---|
| **任务可并行** | ✅ | 基本面 / 技术面 / 舆情 / 宏观四类分析彼此独立,可同时进行 |
| **角色可专精** | ✅ | 各自需要不同的工具集、prompt 与数据源 |
| **单上下文装不下** | ✅ | 财报 + 数十条新闻 + 行情数据远超单次上下文预算 |
| **需要对抗视角** | ✅ | 分析师的确认偏误会被 LLM 原样继承,需要多空对立论证 |

**四条全部命中 → 多 Agent 成立。**

其中**第三条是第一性理由**:即便不考虑并行与专精,单 Agent 也无法在一个上下文里容纳一次完整研究所需的全部材料。多 Agent 的"子任务隔离 + 结构化回传"是对这个约束的直接回应。

### 反向约束:承认多 Agent 的负收益区间

对简单问题(如"某公司最新市盈率是多少"),多 Agent 更慢、更贵,收益为负。

**因此系统内置 Router**:先判定问题复杂度,简单问题直接走单 Agent,不启动编排流程。

> 承认边界与实现能力同等重要。**一个不会退化为单 Agent 的多 Agent 系统,是设计缺陷而非优点。**

---

## 决策二:每个 Agent 必须通过消融实验自证价值

### 机制

1. **增量引入**:M2 阶段先上 2 个 Analyst 跑通全流程,再逐个添加
2. **消融验证**:每引入一个 Agent,在评测集上做 A/B —— 有它 vs 没它
3. **去留由数据决定**:边际贡献不显著或为负的 Agent,**直接删除**
4. **持续复核**:模型升级或 prompt 变更后,消融结论需重新验证

### 当前各 Agent 的去留判据

| Agent | 判据 | 预期风险 |
|---|---|---|
| Router | 分流准确率 + 成本节省 | 低 |
| Orchestrator | 必需(编排核心) | — |
| Fundamental Analyst | 消融实验 | 低(投研主干) |
| Technical Analyst | 消融实验 | 中 |
| Sentiment Analyst | 消融实验 | 中 |
| Macro Analyst | 消融实验 | **高 —— 最可能被砍** |
| Bull / Bear 辩论 | 开/关 A/B | 中(可能只在争议标的上有效) |
| Portfolio Manager | 必需(冲突裁决) | — |
| Critic | 无出处结论率对比 | 低 |

### 为什么这条机制重要

它把"不堆砌技术"从一句原则变成了**可执行、可验证的工程机制**:

- Agent 的去留由**评测数据**决定,不由架构图决定
- 每个 Agent 的存在都有量化依据,面试时可以逐个说明"它贡献了多少"
- 允许出现"我砍掉了 X Agent,因为消融证明它没有贡献"这样的结论 —— **这比多留一个 Agent 更有说服力**

---

## 后果

**正面**
- 架构的每一部分都有实证支撑,不存在"为了多 Agent 而多 Agent"
- 产出的对比数据(A/B + 消融)本身就是项目最核心的资产
- 系统对简单问题不会付出多 Agent 的代价

**负面**
- 前期需要先建评测体系才能验证 Agent 价值,开发顺序被约束(评测必须先行)
- 消融实验需要额外的评测成本(每个 Agent 一组对照)

**缓解**
- 消融实验用评测子集 + 快模型跑,控制成本
- 评测批跑走离线队列,不影响在线路径
