# ADR 001 · 服务边界:为什么是模块化单体 + 3 个独立部署单元

- **状态**:已采纳

---

## 背景

系统包含入口鉴权、多 Agent 编排、检索、金融数据、模型路由、代码执行、评测等多个关注点。
初版设计曾拆为 8 个微服务(gateway / agent-core / rag-service / data-service / llm-gateway / sandbox-runner / harness / frontend)。

## 问题

**这些关注点应该拆成几个可独立部署的单元?**

## 决策

**拆成 4 个部署单元:`frontend` / `api`(模块化单体)/ `worker` / `sandbox-runner`。**
其余关注点作为 `api` 内部模块存在,`harness` 作为 CLI 而非服务。

### 拆分判据

一个关注点独立成服务,必须至少满足以下之一:

1. **安全边界** — 必须进程/容器级隔离
2. **资源与生命周期差异** — 扩缩容模型或失败模式显著不同
3. **独立发布节奏** — 有独立的团队或迭代周期
4. **独立扩容需求** — 负载特征与主服务显著不同

### 逐项裁定

| 关注点 | 判据命中 | 结论 |
|---|---|---|
| **sandbox-runner** | ① 安全边界 —— 执行 LLM 生成的代码,必须隔离 | ✅ 独立 |
| **worker** | ② 生命周期 —— 多 Agent 任务运行数分钟,采用 Durable Execution 模型(检查点、心跳、孤儿回收、可挂起恢复),与短请求 API 的扩缩容模型、超时策略、失败恢复方式完全不同 | ✅ 独立 |
| **frontend** | 独立构建产物与部署方式 | ✅ 独立 |
| gateway(认证/限流/注入过滤) | 无 —— 是请求处理链路的一环 | ❌ 作为中间件模块 |
| rag(检索) | 无 —— 当前单一消费方,负载与 api 同源 | ❌ 模块 |
| data(金融数据) | 无 —— 本质是数据访问层 | ❌ 模块 |
| llm(模型路由) | 无 —— 单一消费方时独立服务收益为零 | ❌ 模块 |
| memory(记忆系统) | 无 —— 与 agents 共享 Postgres,读写路径同源 | ❌ 模块 |
| **MCP Server**(对外暴露能力) | 无 —— 复用同一套工具实现与权限校验,拆开会导致实现分叉或旁路风险 | ❌ 挂载于 api 的独立路由与认证通道 |
| harness(评测) | 不是在线服务 —— 在 CI 与本地批量运行 | ❌ CLI / 库 |

## 理由

**拆分的收益必须大于成本。** 在单人 / 单团队、无独立扩容需求的前提下,微服务的成本是实打实的:

- 一次字段变更要同步多个服务与契约
- 本地开发需要启动全部依赖,迭代摩擦显著
- 跨服务调试链路变长,而本项目最需要的产出是**评测数字**,不是服务数量
- 分布式带来的一致性、重试、幂等问题,在没有真实需求时属于自找的复杂度

同时,**模块化单体不等于放弃边界**:

- 每个模块有独立的 `schemas`,依赖单向(`agents` → `rag`/`data`/`llm`/`memory`,反向禁止)
- 模块间只通过明确的接口调用,不共享内部状态
- 因此**任何模块都可以在需要时低成本抽离为独立服务**

### 关于 MCP Server 的边界说明

MCP Server 对外暴露研究能力,形态上像是"另一个服务",但它**不应成为独立部署单元**:

- 它必须复用同一套工具实现、参数校验与权限检查。拆成独立服务会产生两条调用路径,长期必然分叉,并可能出现绕过 PIT 约束等旁路风险
- 独立的部分是**接入通道**(协议适配、认证、配额计量),而非**能力实现**

因此实现为 api 内的独立路由 + 独立认证与计量通道,共享底层工具注册表。

## 未来触发条件(什么时候会再拆)

| 模块 | 抽离触发条件 |
|---|---|
| **rag** | 嵌入 / rerank 出现独立扩容需求(如需要 GPU 实例),或检索 QPS 与主 API 出现数量级差异 |
| **llm** | 出现多个消费方需要统一的成本管控与配额,或需要独立的模型灰度发布节奏 |
| **data** | 数据同步任务变为常驻 ETL,与在线查询产生资源竞争 |
| **memory** | 记忆检索出现独立扩容需求,或需要跨系统共享记忆 |
| **gateway** | 需要在多个后端服务前统一鉴权,或引入独立的 API 网关产品 |
| **MCP Server** | 外部消费方规模化,需要与内部流量做物理隔离和独立限流 |

## 后果

**正面**
- 本地 `docker compose up` 启动快,迭代摩擦低
- 跨模块重构成本低,适合早期快速演进
- 保留了真实且有理由的服务拆分(安全隔离、异步执行),微服务能力仍有体现

**负面**
- `api` 单体在极端负载下只能整体扩容(当前无此需求)
- 模块边界依赖工程纪律维持,需要通过依赖检查与 code review 保证不被侵蚀

**缓解措施**
- CI 中加入模块依赖方向检查,防止边界被破坏
- 每个模块保持独立测试集,确保可抽离性
