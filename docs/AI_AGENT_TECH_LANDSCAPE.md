- 每个领域末尾的「工程难点」是真正区分"能跑"与"能用"的地方

## 1. 模型与推理层

| 技术点 | 说明 | 优先级 |
|---|---|---|
| **模型选型与分层** | 强模型做规划/综合,快模型做执行/分类。成本可差 10× | P0 |
| **Extended Thinking / 推理模式** | 复杂规划开启深度思考,简单任务关闭以省成本 | P0 |
| **参数控制** | temperature / top_p / max_tokens 按 Agent 角色差异化配置 | P0 |
| **流式输出(Streaming)** | SSE 逐 token 推送,长任务体验关键 | P0 |
| **Prompt Caching** | 系统提示 / 工具定义 / 长文档缓存,显著降本降延迟 | P0 |
| **多供应商抽象** | 统一接口封装不同厂商 SDK,支持故障切换 | P0 |
| **Token 计数与预算** | 请求前预估、运行中累计、超限熔断 | P0 |
| **批处理(Batch API)** | 离线评测批量跑,成本可减半 | P1 |
| **结构化解码** | 约束生成保证输出符合 schema | P1 |
| **本地/开源模型** | vLLM / Ollama 部署小模型做分类、rerank 等轻任务 | P2 |
| **模型微调 / 蒸馏** | 用强模型轨迹蒸馏小模型,专项任务降本 | P2 |

**工程难点**:模型能力边界模糊,同一 prompt 在不同模型上表现差异大 → 必须靠评测集(见 §10)客观选型,而非凭感觉。

## 2. Agent 核心循环

| 技术点 | 说明 | 优先级 |
|---|---|---|
| **ReAct 循环** | Thought → Action → Observation 迭代,Agent 的基本骨架 | P0 |
| **任务规划(Planning)** | 复杂任务拆解为子任务 DAG;显式 plan vs 隐式规划 | P0 |
| **反思(Reflection)** | 失败后自我批判并重试,而非直接放弃 | P0 |
| **自我校验(Self-Verification)** | 输出前自查:引用是否存在、数字是否勾稽 | P0 |
| **终止条件设计** | 何时算"完成";步数上限 / 预算上限 / 置信度阈值 | P0 |
| **循环检测** | 识别 Agent 陷入重复动作并强制打断 | P0 |
| **Plan-and-Execute** | 先出完整计划再执行,vs 边走边想,各有取舍 | P1 |
| **Tree of Thoughts / 多路径搜索** | 并行探索多条推理路径后择优 | P2 |
| **CoT 自洽性(Self-Consistency)** | 多次采样投票,提升确定性任务准确率 | P2 |

**工程难点**:**终止条件是最被低估的难点。** 停太早=答案不完整,停太晚=烧钱且发散。成熟做法是"步数上限 + token 预算 + 质量判定"三重控制,而非单一条件。

## 3. 工具调用与工具工程

| 技术点 | 说明 | 优先级 |
|---|---|---|
| **Function Calling** | 工具 schema 定义、参数校验、结果回传 | P0 |
| **工具设计原则** | 描述即 prompt;工具粒度、命名、错误信息都直接影响成功率 | P0 |
| **入参校验** | LLM 生成的参数必须严格校验,防注入/越界 | P0 |
| **工具错误处理** | 错误信息要"对 Agent 友好",能引导它自我修正 | P0 |
| **并行工具调用** | 一轮内并发调用多个独立工具,压延迟 | P0 |
| **代码执行工具** | **数值计算交给代码,LLM 不做算术** — 治理数值幻觉的关键手段 | P0 |
| **沙箱隔离** | 代码执行必须在容器/受限环境中,资源与网络受限 | P0 |
| **MCP(Model Context Protocol)** | 标准化工具/数据源接入协议,可对接外部 MCP Server | P1 |
| **工具检索(Tool RAG)** | 工具数量多时,先检索出相关工具子集再交给模型 | P1 |
| **工具权限位** | 每个工具绑定权限,按角色/租户授权 | P1 |
| **计算机使用 / 浏览器自动化** | 抓取无 API 的数据源 | P2 |

**工程难点**:**工具越多,选错工具的概率越高**(工具混淆)。解法:工具分组 + 按 Agent 角色只暴露必要工具 + 对工具描述本身做 A/B 评测。

## 4. 上下文工程 ⭐

> 当前 Agent 工程最核心的能力。多 Agent 系统的 token 成本和错误率,几乎都由上下文管理决定。

| 技术点 | 说明 | 优先级 |
|---|---|---|
| **上下文隔离** | 子 Agent 只收到自己的子任务,不带全量历史 | P0 |
| **结构化回传** | 子 Agent 返回结构化结论而非原始全文,防上下文爆炸 | P0 |
| **上下文压缩(Compaction)** | 长会话滚动摘要,保留关键事实丢弃冗余 | P0 |
| **上下文卸载(Offloading)** | 大块内容存外部(文件/DB),上下文只留引用句柄 | P0 |
| **Just-in-time 检索** | 需要时才拉取,而非预先塞满上下文 | P0 |
| **中间遗忘(Lost in the middle)** | 长上下文中间部分注意力弱 → 关键信息放首尾 | P1 |
| **上下文预算分配** | 给系统提示/工具/历史/检索结果各分配 token 配额 | P1 |
| **注意力预算与降级** | 接近上限时主动裁剪低价值内容 | P1 |

**工程难点**:**N 个 Agent 各带全量历史 → token 随 N 线性甚至平方增长。** 这是多 Agent 从"能跑"到"能用"的分水岭。核心解法是"子任务隔离 + 结构化回传",把增长压回常数级。

## 5. 记忆系统

| 技术点 | 说明 | 优先级 |
|---|---|---|
| **短期记忆** | 单次会话内的状态与历史 | P0 |
| **长期记忆** | 跨会话持久化(用户偏好、历史结论) | P0 |
| **记忆分类** | 情景记忆(发生过什么)/ 语义记忆(事实知识)/ 程序记忆(怎么做) | P1 |
| **记忆写入策略** | 什么值得记?自动抽取 vs 显式写入 | P1 |
| **记忆检索** | 按相关性/时效性召回,注入当前上下文 | P1 |
| **记忆更新与冲突消解** | 新事实与旧记忆矛盾时如何取舍 | P1 |
| **记忆衰减 / 遗忘** | 过期信息降权或清除,防陈旧知识污染 | P2 |
| **共享记忆(多 Agent)** | Agent 间共享黑板(blackboard),避免重复劳动 | P1 |

**工程难点**:记忆不是越多越好。**无节制写入会让检索噪声上升、上下文被垃圾占满。** 需要明确的写入准则和衰减策略。

## 6. 检索增强 RAG

| 技术点 | 说明 | 优先级 |
|---|---|---|
| **文档解析** | PDF/HTML/表格解析,**表格结构化是难点** | P0 |
| **分块策略(Chunking)** | 固定/语义/递归分块;chunk 大小直接影响召回质量 | P0 |
| **向量检索** | Embedding + 向量库,ANN 索引(HNSW) | P0 |
| **混合检索(Hybrid)** | 向量 + BM25 关键词,融合排序(RRF) | P0 |
| **元数据过滤** | 按实体/时间/类型过滤检索范围 | P0 |
| **重排(Rerank)** | 召回 top-k 后用 cross-encoder 精排 | P0 |
| **引用绑定(Citation)** | 每条结论绑定 source_id,可溯源到原文片段 | P0 |
| **Agentic RAG** | Agent 自主决定检索什么、检索几轮、是否需要补检索 | P1 |
| **查询改写(Query Rewriting)** | 口语问题改写成适合检索的查询;多查询扩展 | P1 |
| **上下文补全(Contextual Retrieval)** | 给 chunk 补文档级上下文再嵌入,提升召回准确率 | P1 |
| **GraphRAG / 知识图谱** | 实体关系图谱,适合多跳关系推理 | P2 |
| **检索独立评测** | 召回率/精确率/MRR/NDCG,单独评测检索链路 | P1 |

**工程难点**:**检索质量决定系统上限。** 生成再强,检索不到就是幻觉。所以检索必须**独立评测**,不能只看端到端效果——否则无法定位问题出在检索还是生成。

## 7. 多智能体系统 ⭐

| 技术点 | 说明 | 优先级 |
|---|---|---|
| **拓扑结构** | 单体 / 流水线 / Orchestrator-Worker / 群体 / 层级 | P0 |
| **Orchestrator-Worker** | 主脑拆任务、派发、汇总 — 最实用的生产拓扑 | P0 |
| **并行 fan-out / fan-in** | 并发执行独立子任务后汇聚 | P0 |
| **角色专精** | 每个 Agent 独立 prompt / 工具集 / 模型档 | P0 |
| **Agent 间通信协议** | 消息 schema、结构化交接(handoff) | P0 |
| **Router 分流** | 简单任务走单 Agent,避免多 Agent 的负收益 | P0 |
| **辩论(Debate)/ 对抗式** | 对立角色各自论证,防单视角确认偏误 | P1 |
| **裁决与共识** | 冲突信号如何汇总(权重/投票/元 Agent 裁决) | P1 |
| **动态编排** | 按任务复杂度动态决定 Agent 数量与深度 | P1 |
| **归因与消融** | 量化每个 Agent 的边际贡献(去掉它掉多少分) | P1 |
| **谄媚 / 趋同治理** | 防止 Agent 互相附和,保持真实对抗性 | P1 |
| **错误传播控制** | 上游 Agent 出错不应污染全链路 | P1 |
| **A2A / Agent 互操作协议** | 跨系统 Agent 通信标准 | P2 |

**核心认知**:**多 Agent 不是越多越好。** 协调开销、上下文成本、错误传播都随 Agent 数增长。只有满足以下条件时才值得:

> ✅ 任务**可并行** ✅ 角色**可专精** ✅ 单上下文**装不下** ✅ 需要**对抗视角**

对简单任务,多 Agent 更慢更贵、收益为负 → 需要 Router 分流。**能讲清这个边界,比能堆 Agent 更有价值。**

## 8. 结构化输出与数据契约

| 技术点 | 说明 | 优先级 |
|---|---|---|
| **强类型模型定义** | 所有 Agent 输出走 schema(如 Pydantic) | P0 |
| **JSON Schema / Tool-based 结构化** | 用工具调用机制强制结构化输出 | P0 |
| **校验失败重试** | schema 不合法时自动反馈错误并重试 | P0 |
| **跨服务数据契约** | 共享 schema 包,前后端/服务间类型一致 | P0 |
| **版本化 schema** | 输出结构演进时的兼容策略 | P1 |

**工程难点**:结构化不只是"输出 JSON",而是**让类型系统成为 Agent 与系统之间的契约**——校验失败能自动纠错,才是可用的工程闭环。

## 9. 编排与工作流

| 技术点 | 说明 | 优先级 |
|---|---|---|
| **状态机编排** | 显式定义节点、边、条件跳转(如 LangGraph) | P0 |
| **状态持久化(Checkpointer)** | 状态落库,支持中断恢复 | P0 |
| **条件路由** | 按运行时状态决定下一步 | P0 |
| **循环与上限** | 带上限的重试 / 补查循环 | P0 |
| **Human-in-the-Loop** | 中断挂起 → 人工审批 → 恢复执行 | P0 |
| **异步任务队列** | 长任务转后台,队列 + 状态轮询 | P0 |
| **超时与熔断** | 每节点超时控制,下游故障熔断降级 | P0 |
| **多轮交互与会话管理** | 跨轮次上下文、澄清追问 | P0 |
| **持久化执行(Durable Execution)** | 崩溃后从检查点恢复,不重跑全部 | P1 |
| **幂等性** | 重试不产生重复副作用 | P1 |
| **子图复用** | 常用流程封装成可复用子图 | P1 |

**工程难点**:Agent 任务往往是**长时、易失败、有副作用**的。把它当"一次 HTTP 请求"处理必然崩;必须按**可恢复的长事务**设计。

## 10. 评测体系 / Harness Engineering ⭐⭐

> **没有评测的 Agent 项目,无法证明任何主张。** 这是区分"demo"与"工程"的分水岭。

| 技术点 | 说明 | 优先级 |
|---|---|---|
| **评测集构建(EvalSet)** | 分层样本:事实类 / 分析类 / 决策类 | P0 |
| **端到端评测** | 最终输出质量打分 | P0 |
| **组件级评测** | 检索、工具调用、单 Agent 分别评测 | P0 |
| **LLM-as-Judge** | 用模型按 rubric 打分 | P0 |
| **Judge 校准** | 人工标注子集验证 judge 与人的一致性 | P1 |
| **客观 Ground Truth** | 有唯一答案的任务精确匹配;有客观后验的用真实结果判分 | P0 |
| **轨迹评测(Trajectory Eval)** | 不只看答案,看执行路径是否合理(工具选择、步数) | P1 |
| **A/B 对比实验** | 单 vs 多 Agent、不同模型、不同 prompt | P0 |
| **消融实验(Ablation)** | 去掉某组件,量化其贡献 | P1 |
| **回归测试与门禁** | CI 每次提交跑评测,分数下降则阻断合并 | P0 |
| **Trace 回放(Replay)** | 失败样本一键复现调试 | P0 |
| **成本 / 延迟基准** | 每次评测记录 token、耗时、费用 | P0 |
| **方差与稳定性** | 同一样本多次运行的分数波动 | P1 |
| **防过拟合** | 时序切分 / 留出集,防在评测集上过拟合 | P1 |
| **多重检验修正** | 试了 N 组配置总有几组好看 → 需统计修正 | P2 |
| **公开 Benchmark 对标** | 接入行业基准做横向对比 | P2 |

**工程难点**:**LLM-as-judge 本身也会错、也有偏见**(偏爱长答案、偏爱自己家模型)。必须用人工标注子集校准 judge,否则评测本身不可信。

## 11. 可观测性

| 技术点 | 说明 | 优先级 |
|---|---|---|
| **分布式追踪** | 跨服务 trace,每个 Agent/工具一个 span(OpenTelemetry) | P0 |
| **结构化日志** | 全链路 trace_id 贯通,JSON 日志 | P0 |
| **GenAI 语义约定** | 按 OTel GenAI semconv 记录模型/token/成本属性 | P1 |
| **LLM 专用可观测** | prompt/completion 级检查、版本管理、人工标注(如 Langfuse) | P1 |
| **指标(Metrics)** | QPS、延迟分位、错误率、token 速率 | P0 |
| **成本核算** | 按请求/Agent/模型/租户维度统计花费 | P0 |
| **执行树可视化** | 把一次多 Agent 运行渲染成可展开的树 | P0 |
| **会话回放** | 完整重现一次运行的每一步 | P1 |
| **告警** | 成本异常、错误率飙升、评测分数下跌 | P1 |

**工程难点**:Agent 系统的失败往往是**"结果不好"而非"报错"**。传统 APM 看不出问题,必须做到 **prompt / 中间结论 / 工具调用级别**的可见性。

## 12. 安全与治理

| 技术点 | 说明 | 优先级 |
|---|---|---|
| **Prompt Injection 防护** | 输入过滤(正则+语义)+ 工具入参二次校验 | P0 |
| **间接注入防护** | 检索到的文档/网页中可能藏指令 → **外部内容一律视为数据而非指令** | P0 |
| **输出护栏(Guardrails)** | 敏感内容、越权结论、合规红线拦截 | P0 |
| **工具沙箱** | 代码执行容器隔离,资源/网络/文件系统限制 | P0 |
| **认证与鉴权** | JWT + RBAC,细粒度权限 | P0 |
| **敏感数据治理** | PII 脱敏、字段级权限 | P1 |
| **多租户隔离** | 数据与向量库按租户隔离 | P1 |
| **操作审计** | 每次工具调用/数据访问落审计日志,可追责 | P0 |
| **速率限制与配额** | 按用户/租户限流,防滥用与成本失控 | P0 |
| **人机协同审批** | 高风险动作强制人工确认 | P0 |
| **合规红线** | 业务禁区硬编码拒绝 | P0 |
| **密钥管理** | API Key 不落代码,环境变量/密钥服务 | P0 |

**工程难点**:**间接注入是 Agent 特有的、最被忽视的攻击面。** Agent 会读取外部内容(网页、文档、邮件),其中的恶意指令可能被当成命令执行。**核心原则:工具返回的一切内容都是数据,不是指令。**

## 13. 成本与性能优化

| 技术点 | 说明 | 优先级 |
|---|---|---|
| **模型分层路由** | 按任务难度选模型档 | P0 |
| **Prompt Caching** | 复用长系统提示与文档前缀 | P0 |
| **并行化** | 并发 Agent / 并行工具调用压延迟 | P0 |
| **Token 预算控制** | 全局预算 + 动态分配 + 超限收敛 | P0 |
| **上下文裁剪** | 见 §4 | P0 |
| **流式 + 渐进渲染** | 感知延迟优化 | P0 |
| **语义缓存** | 相似问题命中历史结果 | P1 |
| **批处理** | 离线任务走 Batch API | P1 |
| **成本-质量帕累托曲线** | 用评测数据画出成本 vs 质量前沿,指导选型 | P1 |

**工程难点**:成本优化必须**以评测为前提**——否则"省了钱、掉了质量"你根本不知道。**帕累托曲线**才是正确的决策依据,而非单看成本。

## 14. 优化与自改进

| 技术点 | 说明 | 优先级 |
|---|---|---|
| **Prompt 版本管理** | prompt 作为代码管理,可回滚、可 A/B | P0 |
| **失败案例回流** | 线上失败样本自动进评测集,形成数据飞轮 | P1 |
| **自动 Prompt 优化** | 用评测反馈自动迭代 prompt(如 DSPy 思路) | P2 |
| **路由策略学习** | 根据历史效果自动调整模型/Agent 路由 | P2 |
| **信号融合 / 权重学习** | 多 Agent 输出的加权组合(ensemble) | P2 |
| **轨迹蒸馏** | 用强模型轨迹训练小模型降本 | P2 |

**工程难点**:自改进的前提是**可靠的评测信号**。评测不准,自动优化只会朝错误方向狂奔。

## 15. 部署与运维

| 技术点 | 说明 | 优先级 |
|---|---|---|
| **容器化(Docker)** | 每服务独立镜像,多阶段构建瘦身 | P0 |
| **编排(docker-compose)** | 一键拉起全栈依赖 | P0 |

## 附录 · 能力自查清单

用于快速评估一个 Agent 系统的成熟度:

**基础层(能跑)**
- [ ] ReAct 循环 + 工具调用 + 结构化输出
- [ ] 终止条件与步数上限
- [ ] 流式输出

**工程层(能用)**
- [ ] 上下文隔离与压缩策略
- [ ] 状态持久化与失败恢复
- [ ] 分布式追踪 + trace_id 全链路
- [ ] 注入防护(含间接注入)+ 工具沙箱
- [ ] 模型分层 + token 预算 + 成本核算

**成熟层(能信)**
- [ ] 分层评测集 + 客观 ground truth
- [ ] 组件级评测(检索独立评测)
- [ ] CI 评测门禁(分数下降阻断合并)
- [ ] Trace 回放调试
- [ ] LLM-judge 校准

**深度层(能碾压)**
- [ ] A/B 对比:单 Agent vs 多 Agent 的量化结论
- [ ] 消融归因:每个组件的边际贡献
- [ ] 成本-质量帕累托曲线
- [ ] 动态编排(按复杂度伸缩)
- [ ] 失败案例回流形成数据飞轮
